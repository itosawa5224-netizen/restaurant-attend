## 1. 概要

### 1.1 システム名

**飲食店向けアテンド業務支援システム**\
Restaurant-Attendant Support System

### 1.2 システム概要

### 1.3 背景・課題
　飲食店における繁忙時では、土日祝日のランチタイム・大型連休・年末年始などに利用客が集中して長時間行列を作る。\
　紙の受付表や口頭での情報共有を中心とした従来の店舗運営では、従業員にとって次のような<課題>が発生しやすく、膨大な業務負担となる。

**<課題>**
-   一つの受付表をフロアリーダーのみが確認するため、待機客の把握・空席把握・案内席判断・スタッフへの口頭指示などの業務がその一人に集中する
-   案内席の決定には、人数やその構成・車椅子などの有無・利用客の希望・空席状況などから複合的な判断が必要なため、業務負担が大きい
-   ホールスタッフは待機客状況を確認できず、バッシング(：利用客退店後のテーブル片付け)の優先順位を判断しづらい
-   口頭の情報共有により抜け漏れが生じやすい
-   情報共有に抜け漏れが生じた場合、空席状況を目視確認のうえ席を決定する必要がありタイムロスが生じる


### 1.4 目的
　飲食店繁忙時における、利用客の入店前受付〜席への案内までの「アテンド業務」待機客の状況・空席確認・座席決定・テーブルの片付け指示の情報を一元管理し、スタッフ間でリアルタイムに共有することで、アテンド業務における属人化の解消と口頭指示による情報連携の抜け漏れの防止を目的として開発を行った。\
　加えて、案内席決定・バッシング席の優先順位決定などの判断を補助することで、業務中の「認知負荷」を軽減することを目的とした。

システム導入によりこれらの課題・負担を軽減し、ホールスタッフの根源的業務である「接客」により注力できるようにすることで、サービスの質向上につなげる狙いもある。

### 3.1 開発の範囲


1. 来店客の受付と人数確認
2. 待機客の情報（順番・人数構成など）の確認
3. テーブルの利用状況の管理

5. バッシングの対象・優先順位の判断
6. スタッフ間(複数端末間)での状況共有

　**なお、本システムはあくまで案内席やバッシングの優先順位の "判断を支援" するものであり、最終的な作業決定はスタッフが行うものとする。**

- システムによる座席案内の自動化
- 店長・管理者用機能（座席マスタ設定など）




## 4. 重要な業務ルール（※別ファイルに記載を移動予定）

### 4.1 受付時の登録

受付時には、来店客による席の希望は<ins> 考慮せず </ins>以下の基本情報のみを登録する。

| 項目 | 内容 |
|---|---|
| 名前 | カタカナ |
| 人数構成 | 大人人数・子ども人数など |
| 合計人数 | 人数構成から算出 |
| 備考 | ベビーカーや車椅子の有無 |
| 受付日時 **※** | システムが自動記録 |

※開発後期での実装を検討

### 4.2 席の希望確認について

　席の希望（例：扉付き個室を希望する、など）については、基本的には受け付けず、以下のように扱うこととする。\
　

- 受付時点では、個室希望などの席希望を待機客情報に登録しない。
- 原則として、スタッフが最初に案内した席をお客様に利用してもらう。
- 受付順がきた時点で、希望する席についてお客様から申し出があった場合、または席を確認した上で別の席を希望した場合、席が「使用中」でなければ案内を検討できる。
- 席の希望がある場合について、例外処理の詳細を以下の4.4に示す。


### 4.3 通常時の案内順位・バッシング優先順位

通常時は、**待機客の受付順を最優先**とする。

バッシング待ちテーブルの優先順位は、待機客の受付順と人数、テーブル定員を照合して決める。先頭のお客様を案内できるテーブルを優先して片付ける考え方を基本とする。

### 4.4 席の希望がある場合の例外処理

　受付順が来たお客様が席の希望を申し出る、またはスタッフに案内された席とは別の席を希望した場合、通常の受付順・人数構成に基づくアテンドよりも、希望する席への案内を優先するため、希望席の空席確認と(バッシング未了の場合は)その席のバッシングを最優先に行い、再度アテンドをする。

例：
- 受付順が来た2名のお客様が4人掛け席を希望する。
- 希望の席がバッシング待ちであれば、通常の優先順位にかかわらず、その席をバッシングの最優先対象とする。
- 片付け完了後、スタッフが状況を確認して再度案内する。
- 希望する席が使用中の場合は、別の候補席へ案内する。

**重要：この例外処理は、待機客の受付順そのものを変更するものではない。バッシング対象テーブルの優先順位を変更するものである。**

※希望に合う席が全て使用中の場合、最初に案内した席にするか、希望席が案内可能になるまで再度待機列で待機するかをお客様自身に選択してもらう。

### 4.5 テーブルの状態

テーブルは、少なくとも次の状態を管理する。

| 状態 | 意味 |
|---|---|
| 案内可能 | 片付け・確認が完了している |
| 使用中 | お客様が利用している |
| バッシング待ち | 退店済みで片付けが必要 |

片付け完了後は、担当したスタッフにより「空席・案内可能」に更新する。



## 5. 機能


| ID | 機能 | 概要 |
|---|---|---|
| FR-01 | 受付登録 | 名前・人数構成などを登録し、受付順を付与。<br>待機順を一覧で表示する。 |
| FR-02 | テーブル状態更新 | スタッフの操作により、テーブル状態を<br>「利用中 / バッシング未了 / 案内可能」のいずれかに更新する |
| FR-03 | フロア管理 | 16卓全てのテーブル状態を端末間で共有し、確認する |
| FR-04 | 案内候補提示 | 待機客の人数・受付順・テーブル状態などをもとに案内候補席を提示する |
| FR-05 | バッシング優先順位提示 | 通常ルールと他席要望時の例外ルールに基づき、片付けるテーブルの優先順位を提示する |

### 【重要事項】：システムが提示した順位についての扱い

- 通常時：受付順を最優先し、待機客の人数とテーブル定員を照合して席を決定する。
- 席希望時：受付順が来たお客様の希望に応じて、該当席のバッシングを例外的に優先する。
- 表示された順位はスタッフの判断を支援するものであり、システムが作業を自動確定するものではない。
